# Flow 6: Final judgment and landing

The command keeps its existing name for callers. Its ordinary outcome is a
reviewed change on the selected repository's mainline, not an automatic public
release or production deployment. Upstream promotion is a separate operation.

## Fresh judgment after qualification

Reacquire the current candidate, target base, latest material findings and the
actual qualification result. Confirm the implementation still fits the accepted
product and architecture, has not been superseded, and has sufficient applicable
proof. An unchanged head can receive a new adverse finding. An unrelated base
movement does not automatically require rebase or a complete replay.

Inspect actual shared semantic owners, dependencies, generated inputs and conflict
resolution. Refresh affected proof where the composition requires it. Unknown
impact is not compatibility. A historical gate MERGE recommendation, a green
panel, an empty thread list or a cleanup receipt does not supply this judgment.

The root may perform this review or obtain bounded help from merge-decider,
reviewers or relevant owners. Inspect their evidence. Existing helper roles do
not permit a fixed actor checklist to replace the actual decision.

## Separate consequential operations

A currently reviewed and qualified candidate may be merged only within the
requester's actual authorization and installed repository protection. Use the
normal expected-head protected squash path for ordinary development; preserve
any separately governed source-promotion semantics. No bypass, routine auto-merge
or native merge queue is part of the target method.

Do not create tags, publish packages, create/finalize a GitHub Release, deploy an
external service or promote to another repository from a merge verdict. Those
operations require their own exact authorization, candidate/artifact identity,
proof and recovery owner. `merge_tag_release` is not an ordinary combined action.

Ask repo-operator only for the specific authorized effect. An expected-head guard
protects the PR head but does not atomically freeze the target base. Inspect the
current integration and preserve that residual risk rather than claiming the
entire composition was tested when it was not.

Do not automatically rebase because main advanced. Preserve unique source and
handle genuine conflicts through the existing candidate writer. Never choose
`ours` or `theirs` for evidence/generated files by category; reconcile original
provenance or regenerate from the owning source, then refresh affected proof.

## Read back the landing

An accepted or pending API response is not a verified merge. Resolve ambiguous
responses from current GitHub PR/commit state before retrying. Record the actual
landed commit/tree, source preservation and material differences from the tested
composition. A failed post-merge check does not mean no merge happened.

Do not run the full suite merely because a merge occurred. Retain separately
admitted main health, targeted incident response and release/deep obligations.
The target ordinary main-health batch needs both one hour and ten merges from
its accepted baseline. Existing active workflow behavior remains observable
until its owner qualifies the cutover; this source instruction does not stop it.

Inspect the smallest useful landed behavior/identity and file any genuine
integration failure with exact evidence. Contain affected work and prioritize
repair; demonstrably independent work may continue. A passing main observation
cannot retrospectively authorize an earlier invalid merge.

## Reconcile the claim

Update the issue/PR with the actual result, evidence, remaining product/release
obligations and next useful work. Close only acceptance actually satisfied.
An implementation merged without package/install proof remains unqualified for
those delivery claims. Preserve original failures and changed decisions.

Existing deployment logs and receipts can record observed effects, but file
existence is not success. Do not issue misleading STABLE or NOT_DEPLOYED labels
that erase the distinction between merged source, failed verification and no
attempt. Keep legacy schema compatibility explicit; new semantics require their
own consumer migration.

The selected change may be complete while its larger goal continues. Route
method/product findings to `/flow-7-wisdom` when useful without making a long
Wisdom ceremony a prerequisite to the next independent claim. A blocked merge
returns to the precise Review/Build/Gate owner with source and evidence intact.
