# Flow 3: Build

Own the selected implementation claim through a coherent candidate and useful
proof. Keep repository and build context warm. The root can implement directly
or delegate bounded work; one integrator joins the result. Specialist names are
available capabilities, not a required call checklist.

## Enter from actual work

From repo root, inspect the controlling issue/plan, current candidate and its
production consumers. Existing `.runs/<run-id>/plan/` artifacts may help, but do
not fabricate missing historical steps or regard local invisibility as proof
that an artifact does not exist. Recover it from its actual owner when needed.

Identify the acceptance/rollback boundary, affected semantic owners and direct
dependencies. Preserve existing source and writer ownership. Work in the
selected candidate branch/worktree; do not reset unrelated staging or create a
new branch merely to satisfy a naming recipe.

## Construction and challenge

1. Establish the relevant wrong behavior and the cheapest proof that rejects it.
   Inspect stimulus, oracle, production path and non-vacuity before implementation.
   Preserve original failing cases rather than changing seeds or assertions to
   make the proposed repair look green.
2. Implement at the existing semantic owner and actual consumer. Run focused tests
   as coherent edits become available. Capture the source that actually ran,
   including index/worktree differences, commands, selected/executed subjects,
   outcomes and limitations. An old HEAD plus new dirty bytes is not exact proof.
3. Challenge the completed candidate's coverage and test cost. Look for missing
   error/boundary/compatibility behavior, repeated builds, large fixtures,
   redundant setup and assertions that permit plausible wrong implementations.
   Improve the cheapest effective proof without weakening the accepted claim.
4. Simplify accidental complexity and duplicate authority. Recheck affected
   behavior. Reconcile comments, documentation, configuration, supported entry
   paths and product intent; a helper-only implementation is not user delivery.
5. Apply additional substantive criticism when it can expose a different failure.
   Repair verified findings through the writer and re-review affected questions.
   No fixed polish count permits proceeding with a new defect, and no fixed
   clean-pass count proves sufficiency. Reject invalid findings with evidence;
   record valid deferred work durably with its actual acceptance impact.

Use test-author/test-critic, code-implementer/code-critic, test-executor,
standards-enforcer, mutation-auditor, fuzz-triager, doc-writer/doc-critic or other
existing specialists only when their work is useful. Mutation/fuzz/full suites
are selected proof, not automatic per-edit taxes. A source-only reviewer
must not execute candidate-controlled code; ask the warm worker for an experiment.

A changed premise returns to its owner immediately. There is no mandatory
2–3-call detour before revisiting the plan. Repeated unchanged failure is a reason
to diagnose or change method, not an endless retry rule.

## Publish useful progress

Commit and publish coherent progress early enough for collaboration and recovery.
Use repo-operator or the root's equivalent safe procedure: narrow staging,
actual-surface secret scan, applicable local proof, commit, push and readback.
Preserve unrelated edits. Inspect candidate/base workflow generation before
publication so an old stack cannot unexpectedly request heavy CI.

The target Draft PR exposes source and review evidence; it does not wake costly
CI. No mandatory push after every acceptance criterion, no receipt-only churn,
no empty commit, no automatic Ready transition. If the installed repository
still starts CI on publication, identify that migration constraint and use its
approved publication route; do not disable controls or claim zero execution.

Consume available feedback without waiting for bots. Later feedback goes to the
same claim/writer. A path only accessible in the sender's runtime is not a
completed evidence handoff.

## Record and exit

Reuse existing build receipts and `.runs/<run-id>/build/` helper interfaces when
applicable. Keep original proof distinct from summaries; refresh only evidence
invalidated by actual edits. Record material progress on the issue/PR, not a
second live-state ledger. Do not manufacture counters or mandatory file sets.

A coherent locally challenged candidate goes to `/flow-4-review`. That is not a
merge-ready or installed-product claim. An earlier missing premise returns to
`/flow-1-signal` or `/flow-2-plan`; a real environment/authority blocker receives
a precise checkpoint. Keep useful independent work moving. Completion words
retain the scope defined by CLAUDE.md.
